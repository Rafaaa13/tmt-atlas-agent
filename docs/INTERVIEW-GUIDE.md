# TMT Atlas｜AI 产品与金融岗位面试讲述手册

> 这份手册只写当前已经实现或明确设计的内容。任何用户数量、效率提升、准确率和实时覆盖范围，都必须在真实测试后再填入。

## 一、90 秒项目介绍

我做了一个专注于 TMT 研究的本地优先工作台，叫 TMT Atlas。它解决的是研究材料分散、财务指标口径容易混乱、结论很难追溯的问题。用户可以在一个工作区里完成公司快照、赛道扫描、事件分析和研究备忘录。

我没有把它做成一个只会聊天的金融 Agent，而是把产品实际落地为“来源—证据—事实—确定性计算—推断—人工审阅—备忘录”的本地工作流。收入增速、利润率、单位转换、估值机械计算和可比性检查由本地规则引擎处理；当前已接入的 LLM 能力是对用户在证据审核台明确勾选的证据片段生成草稿，任务解析、结构化抽取、矛盾解释和事件影响链仍属于后续增强，而不是当前已完成能力。这样即使没有模型 API，用户也能完成核心研究；接入 OpenAI-compatible API 后，也只发送用户确认的证据片段。

这个项目同时锻炼了我做 AI 产品和做金融研究的能力：我需要定义用户问题、设计 Agent 边界、处理数据权限和评测，也需要理解财报中的期间、会计准则、分部口径、非 GAAP 指标和证据复核。最终产品不是自动投资建议，而是一个让研究过程更清晰、更可复核的工作台。

## 二、3 分钟项目介绍

### Situation：为什么做

TMT 研究需要同时阅读年报、公告、IR 新闻、表格和研究笔记。研究员最耗时间的往往不是“算一个公式”，而是找到可信材料、对齐口径、确认期间、判断不同来源是否互相矛盾，再把结论写成一份别人能够复核的材料。通用聊天机器人可以快速总结，但容易把模型推断写成事实，也无法自然表达缺失值和不可比数据。

### Task：要解决什么

我要做的不是一个股票推荐机器人，而是一个可以真正完成研究闭环的 TMT 工作台：没有 LLM 也能运行；关键金融计算可以解释；每条重要事实都有来源入口；模型接入后是效率增益而不是唯一依赖；产品可以在 GitHub 上让陌生人快速启动和理解。

### Action：怎么做

我先把核心对象定义为 Workspace、Source、Evidence、Fact、Analysis 和 Memo，建立“来源→事实→计算→推断→备忘录”的数据链。然后选择中美 9 家 TMT 公司作为演示案例，覆盖 AI 基础设施/半导体、云/SaaS、平台/电商/广告三个方向。

在功能上，我先实现无 LLM 的本地路径：公司快照、赛道矩阵、事件影响框架、来源注册表、Markdown/HTML 备忘录和数据边界提示。前端没有从聊天框开始，而是提供研究总览、公司快照、赛道扫描、事件雷达、研究备忘录和来源设置六个任务入口。

在 AI 设计上，LLM 通过 OpenAI-compatible 适配器接入，默认关闭。用户只有在设置中明确开启、配置环境变量并在证据审核台勾选证据后，才能把选定片段发送给模型。当前已完成的是受控研究草稿；任务解析、结构化抽取和多步骤 Agent 仍属于后续路线。定期资讯收集采用 review-first：只访问用户授权的来源，收集标题/日期/链接元数据后进入审核箱，不自动写入已确认事实。

### Result：做到什么

目前已经完成一个可本地启动的 MVP：无需 Docker、数据库服务或 LLM API key，就可以打开工作台、搜索公司与事件、浏览指标与来源、切换赛道、拆解事件并生成 Markdown/HTML 备忘录；同时建立了核心测试和数据边界说明。

目前没有外部用户、生产数据、实时全市场覆盖或效率提升数据，所以我不会把这些写成已经实现的结果。下一步会用 2—5 名同学或同事进行可用性试用，补充真实官方文件的页码证据、SQLite/FTS5、本地文件导入和端到端评测。

## 三、AI 产品岗位可能追问与回答

### 1. 为什么不直接做一个聊天机器人？

因为金融研究的价值不只是生成一段语言，而是把来源、期间、单位、主体和口径管理清楚。聊天框很容易让用户感觉得到答案，但无法知道答案基于什么，也无法区分事实和推断。TMT Atlas 让用户先选择研究任务，进入证据和分析工作台，再在需要时调用模型。

### 2. 为什么 LLM 不是核心？

因为收入增速、利润率、单位换算和可比性判断属于确定性逻辑，应该由代码完成并测试。LLM 更适合自然语言任务解析、跨文档总结和草稿表达。这样既降低幻觉风险，也让没有 API key 的用户仍然可用。

### 3. 你的 Agent 和普通 RAG 有什么不同？

它不是只做“检索几段文本然后回答”的单一步骤，而是把来源、证据、事实审核、金融计算和报告输出拆开。当前可运行的 Agent/模型入口是“对选定证据生成受控草稿”和“授权来源元数据进入审核箱”；任务解析、自动结构化抽取、冲突解释和多步骤自主研究仍是后续扩展。每一步有明确输入输出和失败状态，模型不能跳过事实审核直接写入可信层。

### 4. 为什么要把事实和推断分开？

这是金融场景的信任边界。比如公告直接披露的是某项资本开支计划，这是事实；“可能压低短期自由现金流”是基于事实的推断，应该让用户知道它需要进一步验证。分层后，面试官和研究员都能看见模型到底做了什么。

### 5. 如何评估模型是否可靠？

我会分成几类：引用覆盖率、无证据时拒答率、期间和单位是否混淆、能否识别冲突、数字是否与事实一致，以及 API 失败时是否能降级到本地模式。还要测用户能不能找到来源、理解“演示值”和“待审核”标签，而不是只测语言是否流畅。

### 6. 为什么要默认关闭外部 LLM？

因为研究材料可能是敏感文件，用户需要知道哪些内容会离开本地。默认关闭既符合隐私原则，也保证产品可以离线使用。开启时只允许发送用户选中的证据片段，API key 只从环境变量读取，不写入日志和配置。

### 7. 为什么第一版不做多 Agent 辩论？

多 Agent 很容易变成展示效果，而不是解决用户问题。当前优先保证每一步可解释、可测试和可降级。等单一受控任务图稳定后，如果某个具体环节确实需要多角色审阅，再引入有限的研究员、数据审校和风险审阅角色。

### 8. 如何处理定期自动收集资讯？

采用 review-first。用户先授权来源并选择频率，系统只读取 RSS/Atom/JSON Feed 的标题、日期、链接和来源元数据，去重后放入待审核资讯箱；用户确认后才把它作为研究线索使用，不会未经审阅地改写可信事实。当前它是应用运行期间的本地定时收集器，不是托管后台服务。

### 9. 为什么选这 9 家公司？

它们仍然是演示工作区中的公司对象；当前 bundled demo 数值用于界面和流程演示，不应被描述成 9 家公司的已核验最新财务数据。另有 Baidu、Alibaba、Meta 的小型官方业绩事实集单独存放，和演示指标不混用。选择这组公司是为了演示分部、财年、会计准则和用户指标的可比性问题，而不是声称覆盖整个市场。

### 10. 如何判断产品是否真的好用？

我会观察陌生用户能否按照 README 启动，能否在 10 分钟内完成一个公司快照到备忘录的闭环，能否说出一个指标的来源，能否理解为什么某些数字不可比，能否找到 LLM 开关并理解数据边界。用户任务完成率和误解点比漂亮截图更重要。

### 11. 如果用户想要自动荐股怎么办？

产品会明确定位为研究辅助工具，不提供自动交易、收益承诺或个性化投资建议。如果用户提出观点问题，系统可以整理证据、呈现多种情景和待验证变量，但不会把模型生成内容伪装成确定性投资结论。

### 12. 这个项目最大的产品取舍是什么？

我选择先把“证据可追溯、无 LLM 可用、可测试的金融计算”做好，同时把本地证据导入、事实审核和授权 Feed 收集做成真实的基础能力，而不是一开始做实时行情、多 Agent 辩论和复杂知识图谱。这牺牲了一些炫技效果，但换来了更容易启动、更容易验证、更适合金融场景的核心价值。

## 四、金融岗位可能追问与回答

### 1. 一个公司快照应该看什么？

先做一个公司快照，选取 2—3 个关键指标，再进入证据审核台确认来源、期间、单位和会计口径；随后用金融计算工具跑出公式透明的增长率、利润率或现金流结果，再生成备忘录。对于可比性问题，我会明确展示不可比原因，而不是用一张排名表掩盖不确定性。

### 2. 为什么收入增速不能单独判断公司好坏？

因为增长可能来自低基数、并购、汇率或一次性因素，也可能伴随利润率下降、现金流压力和高资本开支。研究中应该把增速和规模、利润率、研发投入、资本开支、客户质量以及业务分部放在一起解释。

### 3. 中美公司横向比较最容易错在哪里？

财年截止日不同、美元与人民币等币种不同、GAAP/IFRS/中国会计准则不同、分部定义不同、用户指标口径不同，以及管理层披露的非 GAAP 指标不同。TMT Atlas 默认把这些差异标记出来，而不是用一个排名掩盖它们。

### 4. 缺失值为什么不能填 0？

“未披露”与“没有”是两件事。把缺失填 0 会虚构事实，进一步影响增长率、排名和研究结论。产品中把缺失分成未披露、未抽取、不适用和冲突等状态。

### 5. 你如何分析一条事件？

我会先确认事件主体、日期、来源和直接事实，再分析可能影响的业务和指标，最后列出待验证变量、反向证据和不确定性。比如资本开支事件不能直接等于利润下降，需要验证投入规模、投产时间、需求、折旧和现金流影响。

### 6. 研报和官方文件如何分工？

官方年报、公告和监管申报适合作为关键数字和正式披露的主要来源；研报可以帮助形成问题、行业视角和竞争格局，但需要标明是二手观点，不能把研报判断直接当成公司事实。

### 7. 如果两个来源冲突怎么办？

不自动选择看起来更合理的数字。先检查报告期、币种、单位、合并范围、会计准则和指标定义，再展示冲突双方并记录待核验问题。如果无法解决，就让结论保持不确定。

### 8. 你如何解释一个营业利润率计算？

必须确认利润和收入属于同一主体、同一期间、同一币种和同一合并范围，然后使用本地金融引擎的公式；引擎保留分子、分母、公式、单位和警告，遇到零或负分母会阻断，而不是替用户猜测。

### 9. 这个工具能不能替代行业研究员？

不能。它适合减少材料整理、初步结构化和复核成本，但选择研究问题、判断因果、处理反向证据和承担研究责任仍然需要人。产品目标是提升研究工作的可追溯性和效率，而不是消除专业判断。

## 五、最可能被追问的诚信问题

### 没有真实用户，你怎么证明产品有价值？

我不会声称已经证明了大规模价值。目前能证明的是产品可以本地启动，导入本地文件，建立可定位证据，提出并审核事实，运行金融计算，完成核心研究流程。接下来会用 2—5 名同学或同事完成任务测试，记录首次成功时间、完成率、误解点和他们是否能复述产品价值，再决定哪些功能需要修改。

### 你的数据是真实的吗？

当前演示数据明确标记为 illustrative demo，用来验证工作流和界面，不作为实时财务数据。来源注册表保存官方来源入口；正式发布前会把关键数字替换成能定位到官方文件页码/段落的事实，并将示例数据与真实资料分开。

### 你真的做了一个 Agent 吗？

目前已实现可选的 OpenAI-compatible 草稿入口和 review-first 收集计划，完整的多步骤 Agent 会按受控任务图继续扩展。我不会把现阶段的本地规则引擎夸大成已经具备自主研究能力；项目的重点恰恰是展示哪些步骤不应该交给模型。

### 你为什么不直接使用 TradingAgents？

TradingAgents 的多智能体交易研究编排很适合作为参考，但我的产品问题不是自动交易或股票决策，而是 TMT 研究中的材料、证据、口径和备忘录闭环。因此我借鉴其任务分工思路，但把产品边界改成非交易、证据优先和本地优先。

### 为什么没有一开始就接入真实 API？

因为 API 接入会带来数据许可、成本、速率、隐私和供应商依赖问题。先用可复现的本地案例验证产品闭环，才能知道需要什么数据；之后再以独立适配器接入官方公开源，并保留网络失败时的本地降级。

## 六、STAR 版本

### Situation

TMT 研究材料分散，关键指标存在期间、单位、会计准则和分部口径差异；通用 LLM 又可能生成无来源结论。

### Task

做一个同时能体现 AI 产品设计和金融研究能力的本地优先工作台，让用户能够从材料和证据出发完成公司快照、赛道扫描、事件分析和研究备忘录。

### Action

我定义了来源、证据、事实、计算、事件和备忘录六类核心对象，实际实现了本地文件导入、证据定位、pending 事实审核、SQLite 审计、确定性金融计算、官方核验事实分离和授权 Feed 收集器；把 LLM 限定在用户明确选择证据后的受控草稿生成。产品支持中美 9 家 TMT 演示公司、3 个方向、官方来源入口、数据边界提示、事件审阅和 HTML/Markdown 导出；同时实现了 API key 脱敏和 review-first 收集。

### Result

当前已完成可本地启动的 MVP、证据审核台、金融计算工具、授权收集器和 82 项自动测试。无 API key 时，用户可以完成本地材料导入、证据检索、事实审核、搜索、公司快照、赛道矩阵、事件分析和备忘录导出；接入 LLM 后可以对选定证据做语言增强。外部用户、真实效率提升、实时数据覆盖和模型准确率尚未完成验证，因此我会把它们作为下一阶段实验，而不是把它们写成成果。

## 七、产品取舍可讲的失败案例

第一，早期最容易把演示数字误看成真实财报，因此我在数据集、指标卡、README 和报告中都加上演示状态和数据边界。

第二，事件标题很容易被模型扩写成投资结论，因此事件页强制拆分直接事实、推断和待验证问题。

第三，定期收集如果直接写入事实层会放大错误，因此先做授权来源和审阅计划，后续再做自动化执行。

## 八、英文项目介绍（简历/面试）

TMT Atlas is a local-first TMT research workbench that turns public filings, operating metrics, and market events into traceable company snapshots, sector comparisons, event analyses, and exportable research memos. I deliberately separated deterministic financial logic—period, unit, metric, comparability, and formula validation—from optional LLM capabilities such as task planning, evidence summarization, structured extraction drafts, and memo polishing. The core workflow works without an LLM or external API; an OpenAI-compatible adapter can be enabled with explicit consent to send only selected evidence snippets. The project demonstrates AI product thinking, agent boundary design, financial research discipline, provenance, privacy, evaluation, and graceful degradation.
