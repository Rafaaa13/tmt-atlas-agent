# TMT Atlas｜技术架构说明

## 1. 架构决策

TMT Atlas 当前选择“零依赖本地 Web 工作台”作为作品集 MVP，同时已经加入本地证据、SQLite 审核和金融计算模块。原因是产品第一性目标是：陌生人可以按照 README 启动；断网、无 LLM API key 时仍能完成核心研究流程；面试官可以快速看懂产品边界；金融计算和来源链可以被测试。

当前实现由三部分组成：

```text
浏览器
  ↓ HTTP
server.py（Python 标准库）
  ├── AtlasStore：演示数据、来源、设置和本地来源
  ├── Research services：快照、赛道扫描、事件分析、备忘录
  ├── LLM adapter：OpenAI-compatible，可选且显式开启
  └── Static server：提供 frontend/index.html、app.js、styles.css
```

## 2. 为什么不用 LLM 作为核心

财务数字的单位、期间、主体、会计准则和公式必须可解释。模型可以帮助用户表达研究问题、找到相关证据、生成摘要和提出问题，但不应该负责利润率或同比增长的最终计算。

因此当前核心路径全部是本地代码：

- JSON 演示数据加载。
- 公司、指标、事件和来源对象管理。
- 公司快照和来源关联。
- 赛道矩阵与排序。
- 事件影响框架。
- 备忘录 Markdown/HTML 生成。
- 演示数据边界与证据状态提示。

## 3. 数据层

当前 MVP 使用 SQLite 作为本地事实/证据/审计工作区，JSON 文件继续承担可复现演示数据、来源注册表和核验语料的角色。`workspace_db.py` 负责 sources、evidence、facts、audit 四类表，可用 FTS5 搜索并回退到字面 LIKE；`server.py` 通过 `/api/workspace`、`/api/ingest`、`/api/facts` 和 `/api/facts/review` 暴露审核路径。

| 文件 | 作用 |
|---|---|
| `data/demo_seed.json` | 演示公司、指标、事件和常用研究输入问题 |
| `data/source_registry.json` | 官方 IR、SEC、HKEX、SSE 来源入口和限制说明 |
| `data/local_sources.json` | 用户在设置页添加的本地来源元数据 |
| `data/local_settings.json` | LLM/定期收集开关与服务商配置，不保存 API key |

后续可以进一步将公司、事件和备忘录持久化对象统一迁移到 SQLite；目前 evidence/facts/audit 已落入本地数据库，JSON 仍保留为 demo seed 和可导入/导出格式。

## 4. API 边界

当前关键 API：

| 路径 | 作用 |
|---|---|
| `GET /api/health` | 检查服务状态 |
| `GET /api/config` | 获取产品、公司、赛道、提示词和设置状态 |
| `GET /api/search?q=` | 搜索公司、事件和来源 |
| `GET /api/companies/{id}/snapshot` | 获取公司快照和来源关联 |
| `GET /api/sectors/{sector}` | 获取赛道矩阵 |
| `GET /api/events` | 获取事件列表 |
| `GET /api/events/{id}` | 获取直接事实、传导路径、推断和问题 |
| `GET /api/sources` | 获取来源注册表 |
| `POST /api/sources` | 添加本地来源元数据 |
| `POST /api/memos` | 生成本地 Markdown/HTML 备忘录 |
| `POST /api/settings/llm` | 更新 LLM/自动收集设置 |
| `POST /api/llm/draft` | 调用 OpenAI-compatible 草稿接口 |
| `POST /api/collection/plan` | 生成 review-first 资讯收集计划 |

API 返回给前端的是视图模型，不让前端自行重建金融逻辑。指标对象包含展示值、变化值、来源标题、来源 URL、状态和追溯提示。

## 5. Agent 边界

未来扩展为 Agent 时，优先使用受控任务图：

```text
用户问题
 → 任务解析
 → 来源/证据检索
 → 事实抽取草稿
 → 口径/单位校验
 → 确定性计算
 → 事件/可比分析
 → 证据覆盖检查
 → 备忘录草稿
 → 人工审阅
```

每一步使用结构化 JSON/Pydantic 对象交接，不用一大段自然语言在模块间传状态。模型不允许跳过证据和审核直接写入确认事实层。

当前 `POST /api/llm/draft` 实现“对用户选中的证据片段生成草稿”的入口，前端证据审核台负责明确勾选和同意。后续可再加入任务解析、抽取和冲突解释。模型调用要求：

- 用户显式开启。
- API key 只从 `TMT_LLM_API_KEY` 读取。
- 只发送用户选中的证据片段。
- 单次最多发送 12 条证据。
- prompt 明确要求区分事实、计算和推断。
- 返回失败时保留本地功能。

## 6. 定期收集 Agent

定期资讯收集不是“让 Agent 自由浏览互联网”，而是一个有权限边界的流程：

1. 用户添加来源。
2. 用户开启收集计划。
3. 系统展示目标来源、频率和回看窗口。
4. 只读取允许的公开元数据/入口。
5. 去重和排序。
6. 放入待审核资讯箱。
7. 用户确认后再进入事件和事实流程。

当前代码提供 `Collector` 授权 RSS/Atom/JSON Feed 的元数据收集、去重和审核箱；它不会默认执行全网抓取，也不会把资讯自动批准为金融事实。

## 7. 前端信息架构

前端采用单页工作台：

- 研究总览：定位、搜索、常用研究入口、最近事件和公司地图。
- 公司快照：公司身份、关键指标、证据链和近期事件。
- 赛道扫描：公司×指标矩阵、可比性提示、研究检查清单。
- 事件雷达：事件选择、直接事实、传导路径、推断和问题。
- 研究备忘录：选择对象、生成、预览和导出。
- 来源与设置：官方来源、LLM 设置、收集计划、添加来源。

设计上刻意避免“空聊天框优先”：首页先让用户选择一个真实研究任务，再在需要时出现 LLM。这样更适合金融研究，也更能展示 AI 产品的用户体验设计。

## 8. 迁移到生产级作品集版本的路线

第一步，将 JSON 数据层迁移到 SQLite，并新增 `facts`、`evidence`、`audit_log` 表；保留 seed/reset 命令。

第二步，引入 FastAPI/Pydantic，提供严格的数据模型、错误码、请求 ID 和异步任务状态。

第三步，引入 React + TypeScript，保持当前页面信息架构和视觉语言不变，增加路由、组件测试和 Playwright 黄金路径。

第四步，接入 PyMuPDF、CSV/Markdown 解析和页码/行号证据片段，完成用户本地材料导入。

第五步，增加 SQLite FTS5，再根据检索评测结果决定是否加入向量检索。

第六步，接入一个经过许可的官方公开数据适配器，设置缓存、更新时间和失败降级。

第七步，增加模型评测集和 prompt 版本管理，使用黄金答案验证引用忠实度、拒答率和数字一致性。

## 9. 关键取舍

| 取舍 | 选择 | 原因 |
|---|---|---|
| JSON vs 数据库 | MVP 先用 JSON | 零配置、可审阅、易复现；后续再迁移 SQLite |
| LLM vs 规则 | 规则先行 | 金融计算可测试、无 API 也能用 |
| 多 Agent 辩论 vs 任务图 | 任务图 | 更容易定位错误、控制成本和讲清产品边界 |
| 复杂图表 vs 表格/时间线 | 表格和时间线先行 | 研究员先需要口径和证据，不需要装饰性图表 |
| 自动抓全网 vs 授权来源 | 授权来源 + 审阅计划 | 尊重版权、权限、速率和金融研究责任 |
| PDF 导出 vs HTML/Markdown | HTML/Markdown 先行 | 无额外依赖，便于检查内容和版本控制 |

## 10. 安全与隐私

API key 不写入本地设置文件；用户材料不默认上传；LLM 开关默认关闭；模型调用只接收用户选中的片段；对外部来源的访问需要显式来源元数据；示例数据和来源许可分开管理；公开仓库不提交内部实习材料和敏感信息。
